# vector_db 模块设计文档

> 模块：`plugins/vector_db/` · 组：向量数据库 · 更新：2026-09-22

---

## 1. 模块定位

**做什么**：文本向量化、建索引、相似检索，并把检索结果的**分数尺度**与**可答性信号**
交给编排层。

**不做什么**（边界，避免与 qa 组重叠）：

| 不做 | 归属 |
|---|---|
| 文档解析与分块 | file_mgmt |
| 拒答判定（读阈值、决定拒或不拒） | qa 编排层 |
| 答案生成与拼装 | qa 编排层 |
| 实体关系抽取 | kg |

我们只负责回答一个问题：**问句和哪些分块最相关，相关到什么程度。**

## 2. 分块策略及理由（评分表要求项）

### 2.1 问题

原 `doc_parser` 采用**定长切分**（160 字 + 重叠 24）。这对向量检索有两个问题：

1. **语义边界被打散**：一个 160 字的块可能横跨两节内容。用户问"就绪态和阻塞态的区别"，
   检索到的块里混进了"进程与程序的区别"，答案被噪音稀释。
2. **标题被埋没**："什么是进程"这类问句的关键线索是章节标题，定长切把它埋进了正文中间。

### 2.2 方案

改为**标题优先切分**：以 `【标题】` 为分块边界，一块 = 一节；标题单独存入 `title` 字段，
建索引时把 `title + content` 一起向量化。

超长章节（> chunk_size）内部再走定长切，保证不产生超长块。
无 `【】` 标题的文本自动退化为定长切。

### 2.3 实验对比（同题集、同参数、仅分块方式不同）

语料 `evals/vector_db/corpus/os_course.txt`（3 章 23 节，3084 字），评测集 40 题，top_k=3。

| 指标 | heading（标题切） | fixed（定长切） | 差异 |
|---|---|---|---|
| 分块数 | 29 | 28 | — |
| **Hit@1** | **88.9%** | 74.1% | **+14.8%** |
| Hit@3 | 92.6% | 88.9% | +3.7% |
| **MRR** | **0.907** | 0.815** | **+0.093** |
| 库内最低分 | 0.208 | 0.202 | — |
| 无关题最高分 | 0.161 | 0.162 | — |
| 分隔带 | +0.047 | +0.040 | — |

未召回的题（top-3 内无期望章节）：

- `fixed` 未召回：`q01`（什么是进程）、`q07`（进程调度有哪些常见算法）、`q20`（文件的物理结构有哪几种）
- `heading` 未召回：`q01`（什么是进程）、`q40`（内存那一块）

**结论**：标题切在 Hit@1 上带来 14.8 个百分点的提升，MRR 提升 0.093。
理由：把语义边界对齐到章节边界，使单块内容主题单一，向量表示更聚焦。
`q07`、`q20` 在 `fixed` 下未召回而 `heading` 下召回，直接印证了这一点 ——
定长切把"调度算法""文件物理结构"这类清单式内容拆到相邻两块，单块只覆盖一部分选项。

### 2.3b ⚠️ 命中判定修过一个误报（指标因此下调，值得记录）

初版 `run_eval.py` 的 `match()` 在标题前缀不匹配时会**退到 `must_terms`**
（判"词是否出现在正文里"）。实测踩坑：

> `q40`「内存那一块。」的 top-1 是「1.4 进程控制块 PCB」，
> 只因该块正文里有"**内存指针**"三个字，就被判成命中了第 2 章。

结果是 Hit@1 虚高。已改为：**heading 模式下有标题就只按标题判，不再退到 `must_terms`**。

| 指标 | 修正前（虚高） | 修正后（真实） |
|---|---|---|
| Hit@1 | 92.6% | **88.9%** |
| Hit@3 | 96.3% | **92.6%** |
| MRR | 0.944 | **0.907** |
| heading 未召回 | q01 | q01、q40 |

`fixed` 模式无标题可用，仍走 `must_terms`，故数值未变 ——
该路径偏松，**只用于 heading / fixed 的相对比较，不用于绝对值**。

**教训**：正文提一句某词 ≠ 这一节在讲该主题。命中判定的宽松度直接决定指标真假，
宁可指标低一点，也不要一个虚高的数。

### 2.4 分块完整性验证

分块是检索的上游，一旦丢字，那段内容永远召不回，而错因看起来像"LLM 不行"。
因此先验证分块完整性，再做检索评测。

**验证方法**：把原文与所有分块拼接结果去空白后，用 `difflib.SequenceMatcher`
求原文中未被覆盖的片段。为空即无丢字。

> 为什么不用"滑动窗口是否出现"：窗口法会把"重叠量不足"误报成"丢字"。
> 块间重叠按原始字符计（含空白），去空白后有效重叠必然小于配置值，
> 于是长度 = overlap 的窗口必然跨不过边界 —— 但内容其实没丢。

**结果**（5 组参数，两种模式，全部「缺失片段 0」；语料 3084 字）：

| size/overlap | fixed 块数 | heading 块数 | 缺失片段 |
|---|---|---|---|
| 160/24 | 28 | 29 | 0 |
| 80/16 | 66 | 63 | 0 |
| 60/12 | 89 | 78 | 0 |
| 300/50 | 14 | 19 | 0 |
| 120/20 | 39 | 35 | 0 |

**顺带修掉一个缺陷**：原实现 `chunks.append(head.strip())` 会 strip 掉重叠区里的空白，
导致实际重叠字符数少于配置值。实测 `fixed` 模式下配置 overlap=24 时最小块间重叠只有 21，
配置 overlap=12 时只有 9 —— 内容不丢，但跨块短语可能无法完整出现在任何单块中。
已改为内部保留原文、仅输出时 strip。

## 3. Embedding 方案

### 3.1 选型

**字符 unigram + bigram 哈希 + TF 加权，4096 维。**

| 候选 | 为什么没选 |
|---|---|
| 预训练语义模型（bge / m3e） | 需下载模型与依赖，课程环境无法保证；离线可复现优先 |
| 分词后 TF-IDF | 中文分词需 jieba 等第三方库，同样有依赖问题 |
| **字符 n-gram 哈希** | **零依赖、确定性、可复现**，对中文技术文本够用 |

**接入路径**：`embedder.vectorize()` 内部替换即可，`vector_store` 与评测脚本都不用动。
这是刻意的设计——把"换 embedding"的成本压到一个函数。

### 3.2 四个迭代点（都是实测踩出来的）

| # | 问题 | 修正 | 效果 |
|---|---|---|---|
| 1 | "进程"在所有块都出现，泛词主导排序 | **IDF 加权**，`TF × (log((n+1)/(df+1))+1)` | 稀有词权重上升 |
| 2 | 问句里的疑问词稀释信号 | **query 侧只保留语料词表内的 token** | 有效信号占比提升 |
| 3 | "什么是进程"抽到 PCB 内容 | **标题纳入索引**（`title + content`） | 问句与章节主题对齐 |
| 4 | 哈希碰撞污染排序 | 实测 1024/4096/16384 三维度 | **4096 起结果稳定**，定为默认 |

第 4 点的实测依据：1024 维时碰撞噪声使排序抖动，4096 与 16384 结果一致，
故取 4096（维度更低、计算更省）。

bigram 权重设为 unigram 的 2 倍，因为 bigram 携带词序信息，区分度更高。

## 4. 检索打分

### 4.1 公式

```
score = 0.75 × cosine(q, chunk) + 0.25 × keyword_coverage(q, chunk)
```

- `cosine`：query 与 chunk 的 TF-IDF 向量余弦，衡量整体语义相似
- `keyword_coverage`：问句实词中出现在该块正文的比例，衡量**关键信息是否被覆盖**

**为什么加第二项**：纯余弦对短问句不敏感。问句只有 5-6 个字时，向量稀疏，
单个高频词就能主导排序。覆盖率项提供了一个与余弦正交的信号。

### 4.2 分数尺度归一化

两个分项都天然落在 `[0,1]`，加权和也落在 `[0,1]`。

**这一点很关键**：原 `plugins/qa/retriever.py` 的打分（改造前）**没有上界、没有归一化**，
无法作为拒答阈值使用。归一化后编排层才可能用固定阈值判定。
该文件现已按方案 C 改为薄封装，转发到本模块，分数尺度随之一并统一（见第 8 节）。

`score_scale()` 方法显式输出尺度说明，供编排层在判定前读取：

```json
{"formula": "0.75 * cosine + 0.25 * keyword_coverage", "range": [0.0, 1.0],
 "note": "分数尺度由本插件的 embedding 实现决定。更换 embedding 或调整权重后，
          编排层的拒答阈值必须重新标定，否则会出现全拒或全不拒。"}
```

## 5. 拒答阈值标定

### 5.1 方法

按题型统计 top-1 分数分布，寻找「应答题最低分」与「应拒题最高分」之间的分隔带，
阈值取分隔带内偏保守的位置。

**选择策略：先在「零漏答」约束内挑，再最大化正确拒答。**

理由：漏答与误答代价不对等。漏答直接损失准确率分子；误答只影响拒答率分母，
而拒答率是硬条件。所以宁可少拒，不可错拒。

### 5.2 结果

| 分块模式 | 推荐 τ | 判对 | 漏答 | 无关题拒答率 | 诱导题拒答率 | 待澄清 |
|---|---|---|---|---|---|---|
| **heading** | **0.185** | 35/39 (89.7%) | 0 | 8/8 = **100%** | 0/4 = 0% | 1 |
| fixed | 0.182 | 35/39 (89.7%) | 0 | 8/8 = **100%** | 0/4 = 0% | 1 |

任务书硬性条件「库外拒答率 ≥70%」按 out_of_scope 口径已 100% 达标。

**判对率有两个口径，都报出来**：

| 口径 | 算式 | 结果 |
|---|---|---|
| 主口径 | 分母 = 总题数 − 应澄清题数 = 39 | 35/39 = **89.7%** |
| 严格口径 | 把「应澄清」记为误答，分母 = 40 | 35/40 = **87.5%** |

**实测还有一个值得记的结论**：二维扫描（τ + OOV）的「全局最优」与「零漏答口径」
完全重合（都是 35 条）。说明当前题集下**没有「多判对但要多漏答」的余地** ——
判对率的上限被诱导题锁死，靠调 τ 无法再提升。

**分数口径说明**（避免误读）：上表的「库内最低分 0.208」来自
`in_library=True` 的 27 条（24 条 in_scope + 3 条模糊题）。
若只算严格 in_scope 的 24 条，最低分是 `q17`（分段和分页有什么区别）= **0.243**。
两个口径下分隔带分别是 **+0.047** 与 **+0.082**，都成立；
标定取保守口径（+0.047），所以 τ=0.185 偏安全。

### 5.3 核心发现：诱导题拦不住（重要）

```
库内最低分   0.208（严格 in_scope 为 0.243）
无关题最高分 0.161  → 分隔带 +0.047  可分 ✅
诱导题最高分 0.452  → 分隔带 −0.243  不可分 ❌
```

**诱导题**指与语料字面高度重叠、但语料没有其真正所需内容的问句：

| 题 | top-1 分 | 为什么分高 |
|---|---|---|
| q33 PCB 在 Linux 内核源码中对应哪个结构体？ | 0.452 | "进程控制块 PCB"是 1.4 节的高 IDF 词 |
| q34 时间片轮转算法中时间片通常设置为多少毫秒？ | 0.322 | "时间片轮转"直接命中对应章节 |
| q35 银行家算法的具体计算步骤是什么？ | 0.253 | "银行家算法"在语料中出现过 |
| q36 分页系统中页面大小通常设置为多少 KB？ | 0.248 | "分页"是 3 章的核心词 |

**结论**：**这是字面向量的表达上限，不是调参问题。**
字面相似度高 ≠ 语料包含答案。任何单一阈值都无法同时做到「零漏答」与「拦下诱导题」。

实测扫描：τ=0.26 能拦下 2 条诱导题（q35/q36），但会引入 1 条漏答（q17，0.243），
净收益仅 +1 条；τ 再往上（0.29 起）漏答增加快于拦截，净收益转为 0 或负。
**所以不值得为诱导题抬高阈值。**

**正解**：编排层加一道「答案可支撑性检查」——检索到的块里是否真的含有
问句所问的那个具体信息（数值 / 实现 / 步骤）。本模块提供分数与 OOV 两个信号供其使用。

### 5.4 辅助信号 OOV

`analyze()` 输出问句实词中不在语料词表的单字占比：

| 类别 | OOV 均值 | 最高 |
|---|---|---|
| in_scope | 0.02 | 0.12 |
| out_of_scope | **0.65** | 1.00 |
| adversarial | 0.14 | 0.19 |
| vague | 0.15 | 0.33 |

无关题仍可分（0.65 vs 0.02），但 **语料从 1 章扩到 3 章后，诱导题 OOV 从 0.31 降到 0.14** ——
"毫秒""结构体"这类词被新语料吸收了。诱导题与应答题的 OOV 差距被压缩，
**OOV 对诱导题的辅助价值随之减弱**。

**实测作硬门槛收益为 +0 条，故只作辅助提示，不设阈值。**

### 5.5 模糊题的第三态：澄清（本模块只提供信号）

评测集的 `vague` 档 4 条**不能一刀切**，逐条判口径后是 3 答 1 澄清：

| 题 | 问句 | 口径 | top-1 |
|---|---|---|---|
| q37 | 讲讲进程。 | 应作答（指向 1.1/1.2/1.3） | 0.427 |
| q39 | 调度相关的东西。 | 应作答（指向 1.6） | 0.208 |
| q40 | 内存那一块。 | 应作答（指向第 2 章） | 0.280 |
| q38 | 操作系统是怎么管理这些东西的？ | **应澄清** | 0.248 |

**为什么不能靠分数**：q38 的 0.248 **高于**可答题 q39 的 0.208。
抬 τ 会先误伤 q39 和 q17(0.243)，所以判据必须是**字面的**。

**判据**（三条同时成立才澄清）：

1. 分数过闸（≥ τ）—— 否则是拒答，不是澄清
2. 含无先行词的指示代词（"这些""那一块""它"…）
3. **问句锚不到任何章节标题** —— 即语料里没有哪一节在讲它问的东西

第 3 点锚定的是**索引里的全部章节标题**，不是 top-k 命中的标题。原因：
检索失败时 top-k 里根本没有正确章节（q40 的 top-3 全是错的），
若按 top-k 锚定，会把**检索失败**伪装成**口径问题**，两件事就混了。

为此 `vector_store.stats()` 新增 `titles` 字段（去重保序的章节标题表）供锚定使用。

**参考实现与校验**：`evals/vector_db/check_clarify_rule.py`
—— 在 40 题上验证该规则**只**命中 q38，其余 39 题零影响（`[PASS]`）。
qa 组可直接复制其中的 `need_clarify()` 到编排层。

**边界**：本模块**不做澄清判定**（那是编排层职责），只提供
分数、OOV、章节标题表三个信号。判定逻辑与话术由 qa 组定。

## 6. 评测集设计

**40 条**，配比符合任务书要求：

| 类型 | 条数 | 占比 | 要求 |
|---|---|---|---|
| in_scope | 24 | 60% | ≥60% |
| out_of_scope | 8 | 20% | ≥20% |
| adversarial | 4 | 10% | ≥10% |
| vague | 4 | 10% | ≥10% |

**每条带 `expected` 字段**，把期望行为写成机器可读的，避免下一个人猜口径：

| expected | 含义 | 条数 |
|---|---|---|
| `answer` | 应作答 | 27 |
| `refuse` | 应拒答 | 12 |
| `clarify_ok` | 应澄清（既不判对也不判错，单列） | 1（q38） |

`expected` 与 `in_library` 的区别：`in_library` 只回答"语料里有没有这块内容"，
`expected` 回答"系统正确行为是什么"。q38 是 `in_library=false` 但 `expected=clarify_ok`
—— 语料里确实没有"这些东西"所指的内容，但正确行为是追问而不是拒答。

**设计要点**：

1. **配对出题**。同一节内容出两条，一条问机理（应作答）、一条问具体数值/实现（应拒答），
   用来检验系统能否区分「问机理」与「问细节」：

   | 应作答 | 应拒答 | 考察点 |
   |---|---|---|
   | q15 分页存储管理中逻辑地址如何转换为物理地址？（→2.3） | q36 分页系统中页面大小通常设置为多少 KB？ | 机理 vs 数值 |
   | q11 处理死锁有哪几类策略？（→1.8） | q35 银行家算法的具体计算步骤是什么？ | 策略清单 vs 算法步骤 |
   | q04 进程控制块 PCB 中包含哪些内容？（→1.4） | q33 PCB 在 Linux 内核源码中对应哪个结构体？ | 通用概念 vs 具体实现 |

   这三组的字面重叠都很高（"分页""死锁/银行家算法""PCB"），
   是当前失败最集中的地方 —— 结果见 5.3 节。

2. **词面重叠陷阱**。`q02`（进程和程序，→1.3）与 `q05`（线程和进程，→1.5）
   共享"进程""区别"，检验能否区分相邻两节；`q17`（分段和分页，→2.4）
   与 `q15`（分页地址转换，→2.3）、`q36`（页面大小）共享"分页/分段"，
   检验能否在主题簇内正确定位。

3. **表述改写**。`q13`（静态重定位和动态重定位有什么区别）与语料 2.1 节
   "地址重定位，分为静态重定位与动态重定位"措辞不同；
   `q22`（目录的作用是什么）对应语料 3.3 节"目录用于实现文件的按名存取"。
   检验语义匹配而非字面匹配。

4. **章节覆盖**。24 条 in_scope 覆盖语料 23 节中的 18 节
   （未覆盖 3.1 文件与文件系统，该节为总述性内容，不单独出题）。

5. **库外题取自真实场景**，不是随机字符串：天气、食堂、小说、机票、Excel、高铁
   —— 对应"校园问答系统"被问到非课程问题时最可能出现的问法。

## 7. 失败案例归因

`heading` 口径下 4 条失败 + 1 条待澄清（见 `calibration_heading.json`）。

| 题 | 现象 | 根因 | 归类 |
|---|---|---|---|
| q01 什么是进程？ | 未召回（top-1 命中 1.5 节，0.300） | 问句仅 6 字，"进程"在 29 块中出现在 12 块，IDF=1.84 不足以把它拉到 1.1 节 | **问句过短，有效信号不足**，非实现缺陷 |
| q40 内存那一块。 | 未召回（top-3 全错，0.280） | 残缺问句只给了"内存"一个词，检索被 PCB/目录/文件物理结构挤掉 | **模糊题 + 短问句**，叠加分块粒度偏细 |
| q07 进程调度有哪些常见算法？ | 仅 `fixed` 下未召回 | 定长切把 1.6 节的四种算法拆到相邻两块，单块只覆盖一部分 | 分块策略问题，`heading` 下解决 |
| q20 文件的物理结构有哪几种？ | 仅 `fixed` 下未召回 | 同上，3.2 节三种物理结构被拆散 | 分块策略问题，`heading` 下解决 |
| q33 / q34 / q35 / q36 | 该拒未拒（0.248 ~ 0.452） | 字面重叠高但语料无对应内容 | **字面向量硬上限**，需编排层加可支撑性检查 |
| q38 操作系统是怎么管理这些东西的？ | 待澄清（0.248） | 指示代词无先行词，无法锚定章节 | **口径问题**，正确行为是追问，不是拒答（见 5.5） |

**归因结论**：4 条失败里有 4 条（q33–q36）是同一个根因 —— 字面向量无法区分
「字面像」与「真能答」。这不是本模块能靠调参修掉的，必须在编排层加一道
「答案可支撑性检查」。另 2 条未召回（q01/q40）都属**问句过短导致有效信号不足**，
共同特征是问句只给了 6 个字以内的信息。

**没有一条失败是靠调 τ 能修的** —— 这一点很关键：失败集中在
「召回质量」和「答案可支撑性」两端，而 τ 只管中间那一段。

## 8. 与原有检索实现的关系

`plugins/qa/retriever.py` 在本模块接手前已自实现了一套关键词打分，与本模块职责重叠。
组内已决定采用**方案 C 薄封装**：`rag_retriever` 对外接口不变
（`index_files` / `index_chunks` / `retrieve`），内部转发给 `vector_store`。

### 8.1 现状：两者已完全一致

**跑法**：`python evals/vector_db/compare_retriever.py`

| 指标 | `rag_retriever` | `vector_store` |
|---|---|---|
| Hit@1 | 88.9% | 88.9% |
| Hit@3 | 92.6% | 92.6% |
| MRR | 0.907 | 0.907 |
| 分数最大值 | 0.5808 | 0.5808 |
| 分数越界条数 | 0 | 0 |
| 未召回题 | q01、q40 | q01、q40 |

```
[PASS] 两者完全一致 —— 薄封装生效
```

这个脚本现在是**回归校验**：若两者出现不一致，说明有人恢复了旧实现，
分数尺度会重新变得无上界，编排层的拒答阈值随之失效。

### 8.2 改造前的对比（方案选择依据，保留备查）

口径：旧语料 1 章 8 块 / 30 题。**与当前 3 章 29 块 / 40 题不可直接比较。**

| 指标 | 原 `rag_retriever` | `vector_store` |
|---|---|---|
| Hit@1 | 95.0% | 95.0% |
| **Hit@3** | **100.0%** | 95.0% |
| **MRR** | **0.967** | 0.950 |
| 分数上界 | 无（实测最大 1.0722） | 1.0（归一化） |
| 分数越界条数 | 2 | 0 |
| 分隔带 | +0.0666 | +0.0304 |

尺度稳定性实验（同一语义、不同问句长度）：

| 问句 | 原 `rag_retriever` | `vector_store` |
|---|---|---|
| 进程 | 0.8500 | 0.3870 |
| 进程的状态 | 0.7143 | 0.4384 |
| 进程有哪三种基本状态 | 0.6667 | 0.4766 |
| ……以及它们如何转换 | 0.5500 | 0.4968 |
| ……以及这些状态在什么条件下会发生转换 | 0.6667 | 0.6295 |
| **跨度** | 0.3000 | 0.2425 |

**如实记录：就检索质量而言，本模块当时没有优势。**
原实现的关键词直接匹配对短问句很有效，Hit@3 与 MRR 都更高。
所以方案 C 的论据**不是「我们的检索更准」**，而是下面两点：

1. **尺度稳定性**：原实现 `score = 交集比 + 0.35 × 完整词命中数`，
   第二项随问句长度线性增长，实测 2 条分数 > 1。**尺度不封顶意味着阈值不可移植。**
2. **职责归属**：分工表把「向量检索」划归 vector_db 组，交接文档第 10 节写明
   「越界代码在评审时打回」。**两个实现并存，qa 组就无法写统一的拒答判定。**

### 8.3 本模块的实际价值

不在"更准"，而在三点：

1. **分数归一化到 `[0,1]`**，尺度封顶，阈值可标定、可移植。
2. **显式的编排接口**：`score_scale()` 说明分数尺度、`analyze()` 提供 OOV 信号，
   都是给编排层做拒答判定用的。
3. **配套评测链路**：40 题评测集 + 阈值标定 + 分块完整性检查 + 一致性回归校验，
   全部可复现。

代价说清楚：改造后 `rag_retriever` 的分数尺度变了，
若 qa 组在别处对它的分数做过任何硬编码假设，需要同步。目前 fusion 只做排序融合，不受影响。

## 9. 升级路径

按收益排序：

1. **接语义 embedding**（收益最大）。替换 `embedder.vectorize()` 内部实现，
   可直接解决 q01、q40 两条未召回与全部 4 条诱导题。其余代码零改动。
2. **分块加标题前缀**（低成本）。在块正文前拼接章节标题，进一步强化主题信号。
3. **混合检索**（BM25 + 向量）。对专有名词类问句（PCB、FCFS、TLB）效果明显。
4. **重排序**（cross-encoder）。当前 40 条评测集规模下收益有限，不优先。

## 10. 接入基座

模块不是孤立脚本，已按基座规范接入。

### 10.1 节点注册

`config/topology.yaml` 中新增 `vector_db_node`(8102)，插件通过 `entry` 声明式装载：

```yaml
  vector_db_node:
    group: vector_db
    host: 127.0.0.1
    port: 8102
    plugins:
      embedder:
        entry: plugins.vector_db.embedder:EmbedderPlugin
        config: {dim: 4096}
      vector_store:
        entry: plugins.vector_db.vector_store:VectorStorePlugin
        config: {dim: 4096, w_cos: 0.75, w_cov: 0.25}
```

启动：`python -m base.node --node vector_db_node`

### 10.2 远程调用

编排层通过 `RemotePluginProxy` 调用，无需区分本地/远程：

```python
store = RemotePluginProxy("vector_store", "http://127.0.0.1:8102")
store.initialize()                                   # 内部拉取远端 methods()
store.call("search", {"query": "...", "top_k": 3})
```

RPC 信封：`POST /rpc` + `{"id", "method": "vector_store.search", "params"}`。

### 10.3 验证

`smoke_rpc_vector_db.py` 起**真实节点进程**（非 TestClient 假装配），
走完整 HTTP RPC 链路验证 `index` / `search` / `analyze` / `score_scale`：

```
== 节点就绪 == http://127.0.0.1:8102
  node=vector_db_node  plugins=['embedder', 'vector_store']
== 远程建索引 == {'indexed': 29, 'dim': 4096, 'vocab_size': 2158}
== 远程检索 ==
  [库内] 0.4259  [1.2 进程的状态]  进程有哪三种基本状态？
  [库内] 0.5388  [1.8 死锁]  产生死锁的四个必要条件是什么？
  [库外] 0.1608  [1.7 进程同步与互斥]  帮我写一段 Python 快速排序代码。
== 校验 ==
  [PASS] 全部分数落在 [0,1]
  [PASS] 库内最低分 > 库外最高分（存在分隔带）
  库内最低分=0.2850  库外最高分=0.1608  分隔带=+0.1242
```

（该脚本用的是内嵌小样本 query 集，不是完整 40 题评测集，所以分隔带数值与
第 5 节的标定结果不同 —— 它验证的是**链路通不通**，不是阈值好不好。）

**这一条对应交接文档第 10 节的硬要求**：「新插件必须能被 `RemotePluginProxy` 调用，
否则视为未接入基座」。

### 10.4 已知限制

索引为**内存态**，节点重启即丢。demo 流程在每次建图时重建索引即可；
若要常驻服务需另加持久化，当前未实现（不在项目一最低要求内）。

## 11. 复现

```bash
cd campus-qa-system
python smoke_vector_db.py                            # 冒烟（零依赖）
python smoke_rpc_vector_db.py                        # 接入基座验证（需 fastapi/uvicorn）
python evals/vector_db/check_split.py --mode heading # 分块完整性
python evals/vector_db/check_split.py --mode fixed
python evals/vector_db/run_eval.py --split both      # 检索评测（两种分块对比）
python evals/vector_db/calibrate.py --split heading  # 阈值标定
python evals/vector_db/calibrate.py --split fixed
python evals/vector_db/compare_retriever.py          # 薄封装一致性回归校验
python evals/vector_db/check_clarify_rule.py         # 澄清判据校验
```

除 `smoke_rpc_vector_db.py` 外均零第三方依赖，纯标准库，全部结果可复现。

`smoke_rpc_vector_db.py` 用 `sys.executable` 起子进程，
**必须用装了 fastapi/uvicorn 的解释器运行**，否则打印 skip 提示并返回码 2。

### 语料变更后要做什么

语料是本模块唯一的外部依赖，换语料 = 换分数尺度：

1. 按同样格式覆盖 `evals/vector_db/corpus/os_course.txt`（`【标题】` + 正文）
2. 按实际章节改 `eval_set.jsonl` 的 `expect_chunk` 与 `expected`，
   保持配比 ≥60/≥20/≥10/≥10
3. 依次重跑 `check_split.py` → `run_eval.py` → `calibrate.py`
   → `compare_retriever.py` → `check_clarify_rule.py`
4. 把 `calibration_*.json` 里的 `recommend.tau` 重新告知编排层

**不重跑就会全拒或全不拒。**
