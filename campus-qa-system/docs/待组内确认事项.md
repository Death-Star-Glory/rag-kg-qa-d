## 二、已定的三件事（不用再议）

### 1️⃣ 检索归属：方案 C 薄封装 ✅ 已落地

`rag_retriever` 对外接口一字未动（`initialize` / `methods` / `index_files` /
`index_chunks` / `retrieve`），内部改为转发 `vector_store`。
**qa 组不需要改任何代码** —— `fusion.py` 里调的还是 `retriever.retrieve(...)`。

**但有两处需 qa 组知悉**：

1. **分数尺度变了**：改造前无上界（实测最大 1.0722），现在 `[0,1]` 归一化。
   如果别处对分数做过硬编码假设，需要同步。目前 fusion 只做排序融合，不受影响。
2. **返回值多了 `score_scale` 字段**（新增，不是替换，旧代码忽略即可）。

**为什么选 C 而不是「谁更好」**：客观数据（旧语料 1 章 30 题口径）显示
原 `rag_retriever` 的检索质量**不差甚至略优**（Hit@3 100% vs 95%，MRR 0.967 vs 0.950）。
所以论据不是性能，是这两点：

- **尺度**：原实现 `score = 交集比 + 0.35 × 完整词命中数`，第二项随问句长度线性增长，
  实测 2 条分数 > 1。**尺度不封顶意味着阈值不可移植。**
- **归属**：分工表把「向量检索」划归 vector_db 组，交接文档第 10 节写明「越界代码在评审时打回」。
  两个实现并存，qa 组就没有统一的分数尺度可用来写拒答。

**回归校验**：`python evals/vector_db/compare_retriever.py` 输出 `[PASS] 两者完全一致`。
若输出 `[FAIL]`，说明有人恢复了旧实现，**编排层的拒答阈值会随之失效**，请立刻告知我。

### 2️⃣ 模糊题口径：三态（作答 / 澄清 / 拒答）✅ 已落地

## 三、我改了三个组外的文件（报备）

| 文件                                  | 改动                                                                    | 是否影响默认行为           |
| ----------------------------------- | --------------------------------------------------------------------- | ------------------ |
| `plugins/file_mgmt/doc_parser.py`   | ① 修块间重叠不足的缺陷 ② 新增 `split_mode="heading"` 标题切分（默认仍是 `fixed`）③ chunk 加 `title` 字段 | 否（默认行为不变）          |
| `config/topology.yaml`              | 新增 `vector_db_node`(8102) 节点                                           | 否（纯新增）             |
| `plugins/qa/retriever.py`           | 按方案 C 改为薄封装，转发 `vector_store`                                          | 否（接口不变，分数尺度变，见第 1 项） |

**为什么改 `doc_parser`**：分块是检索的上游。实测标题切分让 Hit@1 从 74.1% → 88.9%，
另外 `title` 字段还是「澄清判定」的锚定依据（`fixed` 模式不产出 title，澄清判据不适用）。
所以我在向量库链路上启用了 `heading` 模式，但没有改默认值。

**为什么改 `topology.yaml`**：交接文档第 2 节的分工表里列了 `vector_db_node`，
但 yaml 里没有这个节点，第 10 节又要求「新插件必须能被 `RemotePluginProxy` 调用」，
不补节点就无法验证接入。

**提醒**：如果谁也在改这三个文件，注意冲突。

## 四、指标口径的一处自查（重要，别被问穿）

初版 `run_eval.py` 的命中判定在标题不匹配时会**退到「关键词是否出现在正文」**。
实测踩坑：`q40`「内存那一块。」的 top-1 是「1.4 进程控制块 PCB」，
只因该块正文里有"**内存指针**"三个字，就被判成命中了第 2 章 —— **Hit@1 虚高**。

已修（heading 模式有标题就只按标题判）。修正后：

| 指标     | 修正前（虚高） | 修正后（真实） |
| ------ | ------- | ------- |
| Hit@1  | 92.6%   | **88.9%** |
| Hit@3  | 96.3%   | **92.6%** |
| MRR    | 0.944   | **0.907** |

**所以 88.9% 不是退步，是把虚高的数改成了真数。** 被问到就直接讲这条。

`build_demo_registry()` 创建 `rag_retriever` 时没传后端，会命中薄封装的**第 3 级兜底**

```

stats       -> {'indexed': 28, ..., 'chunk_count': 28}
```

**这是"能用但没跑在最优配置"，不是故障。** 谁负责 demo 谁决定要不要切
